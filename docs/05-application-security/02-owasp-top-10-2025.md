# The OWASP Top 10:2025

> [!TIP]
> **In short:** the OWASP Top 10 is the best-known **awareness list** of the most critical web application risk categories. The 2025 edition (published November 2025) puts **Broken Access Control** first again, moves **Security Misconfiguration** to second, replaces "vulnerable components" with the broader **Software Supply Chain Failures**, folds SSRF into access control, and adds **Mishandling of Exceptional Conditions**. It is a starting vocabulary, not a standard and not a checklist: use it to learn the categories, then use the **ASVS** for requirements and the **Web Security Testing Guide** for testing.

## The list

| # | Category | In one line | Main defense | Where to learn it |
|---|---|---|---|---|
| **A01** | [Broken Access Control](#a01-broken-access-control) | Users act outside their intended permissions; includes SSRF | Deny by default; check every object on the server | [Access control and SSRF](04-access-control-ssrf-and-logic-flaws.md) |
| **A02** | [Security Misconfiguration](#a02-security-misconfiguration) | Insecure defaults, open services, verbose errors, unhardened clouds | Repeatable hardened builds and configuration review | [Hardening](../07-defensive-security/08-hardening-and-resilience.md) |
| **A03** | [Software Supply Chain Failures](#a03-software-supply-chain-failures) | Compromised or vulnerable dependencies, build systems and updates | Inventory, verification, provenance, least-privilege CI | [Secure development](06-secure-development-and-supply-chain.md) |
| **A04** | [Cryptographic Failures](#a04-cryptographic-failures) | Missing or weak protection of data in transit and at rest | Modern algorithms, sound key management | [Cryptography](../04-cryptography-and-identity/01-cryptography-foundations.md) |
| **A05** | [Injection](#a05-injection) | Untrusted data interpreted as code or commands | Parameterized APIs, context-aware encoding | [Injection and XSS](03-injection-and-xss.md) |

| **A09** | [Security Logging & Alerting Failures](#a09-security-logging--alerting-failures) | Attacks that go unrecorded, unnoticed or unanswered | Useful logs, alerts, tested response | [Logging and telemetry](../07-defensive-security/01-logging-and-telemetry.md) |
| **A10** | [Mishandling of Exceptional Conditions](#a10-mishandling-of-exceptional-conditions) | Failures that crash, leak data or fail open | Fail closed, handle errors centrally, test the bad paths | below |

### What changed from 2021

| 2021 | 2025 | Change |
|---|---|---|
| A01 Broken Access Control | **A01** | Still first; now also contains **SSRF** (formerly A10) |
| A05 Security Misconfiguration | **A02** | Up from fifth |
| A06 Vulnerable and Outdated Components | **A03 Software Supply Chain Failures** | Broader: the build, distribution and update chain, not only outdated libraries |
| A02 Cryptographic Failures | **A04** | Down two places |
| A03 Injection | **A05** | Down two places (XSS remains part of it) |
| A04 Insecure Design | **A06** | Down two places |
| A07 Identification and Authentication Failures | **A07 Authentication Failures** | Renamed |
| A08 Software and Data Integrity Failures | **A08 Software or Data Integrity Failures** | Wording changed |
| A09 Security Logging and Monitoring Failures | **A09 Security Logging & Alerting Failures** | Renamed to stress alerting |
| A10 Server-Side Request Forgery | merged into A01 | |
| (none) | **A10 Mishandling of Exceptional Conditions** | New |

The list is built from application-testing data contributed by organizations and mapped to **CWE** weakness types, plus a community survey for risks the data cannot yet show. Rankings reflect incidence across the data, not the severity of one bug. **●●●**

## How to use it (and how not to)

| Do | Do not |
|---|---|
| Use it as a **training baseline** and shared vocabulary | Claim "we are OWASP Top 10 compliant": it is not a standard |
| Map scanner and pen test findings to categories for reporting | Treat the ten items as the only risks that exist |
| Use the **ASVS** to turn a category into verifiable requirements | Use it as a test plan; it is too coarse |
| Use the **Cheat Sheet Series** for implementation guidance | Memorize the order; it changes every few years |
| Build one automated test per category that applies to your system | Rely on a scanner to find A01, A06 or A10 |

| OWASP resource | Job |
|---|---|
| **Top 10** | Awareness: what to learn first |
| **ASVS** (Application Security Verification Standard, version 5.0) | Requirements at three assurance levels; what to build and verify |
| **Web Security Testing Guide** (WSTG) | Procedures: how to test for each weakness |
| **Cheat Sheet Series** | Concise implementation advice per topic |
| **SAMM** | Maturity model for a security program |
| **Juice Shop, WebGoat** | Deliberately vulnerable applications for practice |

## A01 Broken Access Control

**What it is.** The application lets users do or see things beyond their permissions: reading another user's record by changing an ID, calling an admin function, tampering with a token, or making the server fetch internal URLs for them (SSRF). **●●●**

| Typical weaknesses | CWE examples |
|---|---|
| Missing or incorrect authorization | CWE-862, CWE-863, CWE-285 |
| Direct object reference without ownership check | CWE-639 |
| Path traversal | CWE-22 |
| Cross-site request forgery | CWE-352 |
| Server-side request forgery | CWE-918 |

**Prevent.** Deny by default; enforce on the server for every request and every object; scope queries to the caller; log failures; rate-limit sensitive functions; keep CORS narrow; restrict outbound requests from the server. **Test.** Two users and an admin, replaying each request across roles. **Practice.** PortSwigger "Access control" labs, Juice Shop. Full treatment in [Authorization, sessions and federation](../04-cryptography-and-identity/05-authorization-sessions-and-federation.md) and [Access control, SSRF and logic flaws](04-access-control-ssrf-and-logic-flaws.md).

## A02 Security Misconfiguration

**What it is.** The system is secure by design but insecure as deployed: default accounts, unnecessary services and sample apps, directory listing, stack traces in responses, cloud storage left public, permissive CORS, missing headers, XML parsers that resolve external entities (XXE, CWE-611), debug mode in production. Cloud and container platforms multiply the settings that can be wrong. **●●●**

**Prevent.** A repeatable, automated, hardened build (infrastructure as code, golden images); a minimal platform with nothing unneeded installed; the same configuration across development, test and production (with different secrets); automated configuration review against a baseline such as the CIS Benchmarks; segmentation; and security headers (see [Browser security model](01-browser-security-model-and-headers.md)). **Test.** Port and service scans, default credential checks, configuration scanners, cloud posture tools. **Practice.** Harden a fresh Linux VM against a benchmark, then scan it with Lynis and compare before and after.

## A03 Software Supply Chain Failures

**What it is.** Failures anywhere in the chain that produces and delivers your software: vulnerable or abandoned libraries, malicious packages, hijacked maintainer accounts, compromised build servers and CI actions, tampered updates, untrusted registries. It widens the old "vulnerable and outdated components" category. **●●●**

| Case | Lesson |
|---|---|
| **Log4Shell** (2021, CVE-2021-44228) | One ubiquitous library with a critical flaw; most organizations did not know where it ran |
| **SolarWinds** (2020) | The vendor's build system was compromised, so signed, official updates carried malware |
| **xz utils backdoor** (2024, CVE-2024-3094) | A long social-engineering campaign against a single maintainer inserted a backdoor, found by accident |
| **npm worms** (2025) | A self-propagating package compromise stole developer tokens and published more infected packages |
| **CI action compromise** (2025, tj-actions/changed-files) | A widely used build action was altered to leak secrets from the logs of the repositories that used it |

**Prevent.** Keep an inventory (SBOM) of what you ship; scan dependencies; pin versions and verify integrity; prefer fewer, well-maintained dependencies; use private registries for internal names; protect CI with least-privilege tokens and pinned actions; verify provenance of artifacts. Details in [Secure development and supply chain](06-secure-development-and-supply-chain.md).

## A04 Cryptographic Failures

**What it is.** Sensitive data is not protected, or is protected badly: clear-text transport, no encryption at rest, deprecated algorithms (MD5, SHA-1 for signatures, DES, ECB mode), hard-coded or reused keys, weak randomness, ignored certificate validation, passwords hashed with a fast hash. **●●●**

| Typical weaknesses | CWE examples |
|---|---|
| Hard-coded password or key | CWE-259, CWE-321 |
| Broken or risky algorithm | CWE-327 |
| Insufficient entropy | CWE-331 |
| Missing or weak transport protection | CWE-319 |

**Prevent.** Classify data and decide what must be encrypted; use TLS 1.2 or 1.3 with HSTS; use authenticated encryption (AES-GCM, ChaCha20-Poly1305); hash passwords with Argon2id; generate keys with a secure random source and keep them in a key management service; never write your own cryptography. See [Cryptography foundations](../04-cryptography-and-identity/01-cryptography-foundations.md) and [TLS in depth](../04-cryptography-and-identity/03-tls-in-depth.md). **Practice.** Run `testssl.sh` against a server you own and fix every finding.

## A05 Injection

**What it is.** Untrusted data reaches an interpreter as part of a command or query: SQL, NoSQL, operating-system commands, LDAP, template engines, and, on the client side, HTML and JavaScript (cross-site scripting). **●●●**

**Prevent.** Keep data and code separate: parameterized queries, safe APIs that avoid the shell, auto-escaping templates, context-aware output encoding. Validate input with allowlists as a second layer, run databases with least-privilege accounts, and limit result sizes. **Test.** Deliberate malformed input in every parameter, header and cookie, plus static analysis. **Practice.** PortSwigger SQL injection and XSS labs, DVWA. See [Injection and XSS](03-injection-and-xss.md).

## A06 Insecure Design

**What it is.** The flaw is in the design, so a flawless implementation would still be vulnerable: a password-reset flow based on guessable security questions, a booking system without limits that lets one user hold all inventory, a missing rate limit on login, a multi-tenant system with no tenant isolation. **●●●**

**Prevent.** Threat model features before building them; write abuse cases next to use cases; adopt secure design patterns and reference architectures; set resource and rate limits per user and per tenant; separate tiers and tenants; and write security requirements (ASVS) that testers can verify. **Test.** Design reviews and workshop-style threat modeling; business-logic testing. **Practice.** Threat-model the reset flow as in [Threat modeling](../01-foundations/03-threat-modeling.md).

## A07 Authentication Failures

**What it is.** Weak login or session handling: credential stuffing with no defense, default or weak passwords, missing or bypassable MFA, weak recovery, session identifiers in URLs, sessions that survive logout, tokens that are not validated. **●●●**

**Prevent.** MFA (phishing-resistant for privileged users), blocklist and length checks, no default credentials, rate limiting and generic errors, strong recovery, new session IDs at login, server-side invalidation. **Test.** Brute-force and spraying simulations on your own system, session lifecycle checks. **Practice.** PortSwigger "Authentication" labs. See [Passwords and MFA](../04-cryptography-and-identity/04-passwords-and-mfa.md).

## A08 Software or Data Integrity Failures

**What it is.** Code and data are trusted without verifying integrity: auto-update without signature checks, third-party scripts with no Subresource Integrity, pipelines anyone can modify, and **insecure deserialization** of data from untrusted sources (CWE-502). **●●●**

**Prevent.** Verify signatures and digests of updates and dependencies; use SRI for external scripts; require review and protect branches for code and configuration changes; deserialize only data formats with schemas, never native object serialization from untrusted input. **Practice.** The PortSwigger "Insecure deserialization" labs. See [Injection and XSS](03-injection-and-xss.md#insecure-deserialization).

## A09 Security Logging & Alerting Failures

**What it is.** Attacks happen without leaving evidence, or evidence exists but nobody is alerted: logins and access-control failures not logged, logs only on the compromised host, logs that include secrets or can be forged through log injection, no alert thresholds, no tested response. **●●●**

| Typical weaknesses | CWE examples |
|---|---|
| Insufficient logging | CWE-778 |
| Log injection | CWE-117 |
| Sensitive data in logs | CWE-532 |

**Prevent.** Log authentication events, access-control failures and high-value transactions with identity, time, source and outcome; ship logs to a central, protected store; encode log data; define alert thresholds and who responds; rehearse the response. **Practice.** Add structured logging and one alert to your own project, then trigger it with a simulated attack. See [Logging and telemetry](../07-defensive-security/01-logging-and-telemetry.md) and [Detection engineering](../07-defensive-security/02-detection-engineering.md).

## A10 Mishandling of Exceptional Conditions

**What it is.** The application fails to prevent, detect or respond to unusual situations: unhandled exceptions that expose stack traces, error paths that leave transactions half-complete, resource exhaustion, ignored return values, and above all **failing open**, where an error grants access. **●●●**

```python
def is_allowed(user, resource):
    try:
        return policy_service.check(user, resource)
    except Exception:
        return True
```

When the policy service is down or slow, every request is allowed. The secure form fails closed and records the event:

```python
def is_allowed(user, resource):
    try:
        return policy_service.check(user, resource)
    except Exception:
        logger.exception("policy check failed")
        return False
```

| Typical weaknesses | CWE examples |
|---|---|
| Information exposure through error messages | CWE-209 |
| Uncaught exception | CWE-248 |
| Failure to fail securely | CWE-636 |
| Improper handling of exceptional conditions | CWE-755 |

**Prevent.** Apply *fail-safe defaults* (see [Security principles](../01-foundations/02-security-principles.md)); handle errors at the right level and add a global handler that returns a generic message with a correlation ID; use transactions that roll back completely; set timeouts, quotas and limits; validate edge cases (empty, huge, negative, malformed, concurrent). **Test.** Kill dependencies, send malformed and oversized input, fuzz parsers, force timeouts, and verify that the system denies and logs. **Practice.** Add a failing dependency to a lab app and show what each endpoint does.

## Risks outside the Top 10

The list is deliberately short. Real applications also face request smuggling, web cache poisoning, subdomain takeover, race conditions, clickjacking, prototype pollution, regular-expression denial of service, open redirects and many logic flaws. The PortSwigger Web Security Academy topic list is a good map of what else exists.

## Practice

1. Take the table of ten categories and write, from memory, one real incident and one defense for each.
2. In OWASP Juice Shop, solve one challenge from each category that applies and note which category each belongs to.
3. Run a free scanner (OWASP ZAP) against your own lab application and classify each finding by category. Then list the categories the scanner could **not** assess.
4. Choose the ASVS Level 1 requirements that map to one category and test your project against them.

These support [Module 1.4](../../roadmap/phase-1-security-fundamentals/04-web-security-owasp.md) of the roadmap.
